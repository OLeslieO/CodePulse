# Codex Signal v0.2 — 方案 Review

状态更新（2026-09-18）：本方案随后获得用户确认，已进入实现并生成 0.1.0 本地预览版。此文保留确认前的评审记录；当前状态见根目录 README.md。

这是设计评审，不是代码评审，也不是已完成的官方接口核验。用户已确认 Packy Code 文档入口为 https://docs.packyapi.ai/ 。

## 建议批准的产品方向

**Swift 原生 macOS 应用，优先顶部菜单栏，同一状态核心驱动可独立启用的 Caps Lock LED。**

- LED：运行／重试常亮，结构化待审批／待输入／终止异常／工作中观察断线快闪，完成／空闲关闭。
- 菜单栏：快速查看真实余额、可用的用量比例和项目任务状态，展开查看详细原因与更新时间。
- 提供三种模式：仅 LED、仅菜单栏、两者同时启用。
- 第一版不增加侧边浮窗，也不监控任意开发服务器；保留扩展接口。

## 必须解决的实现门槛

| 优先级 | 发现 | 为什么影响方案 | 关闭条件 |
| --- | --- | --- | --- |
| P0 | Desktop 事件覆盖未核实 | 缺少审批解决事件就无法保证及时恢复常亮；独立启动 CLI 不能代替观察 Desktop | 官方接口核验 + 已有 Desktop 实例中的开始、审批、输入、重试、终止、完成事件验证 |
| P0 | LED 独立控制能力未验证 | 某些实现可能实际切换 Caps Lock 逻辑，违反用户要求 | 在目标 MacBook 上证明灯变化但大小写／输入状态不变，且支持释放和唤醒 |
| P0 | Packy Code 账单 API 未核实 | 推理 token 数据不能推导真实余额或套餐使用率 | 官方查询端点、认证及字段证据；否则明确降级并重新确认范围 |
| P1 | 源码级开源比较尚未完成 | 目前不能可靠决定 fork、依赖复用及许可证边界 | 阅读候选仓库并记录 commit、架构、技术栈、许可证和支持限制 |

P0 表示不通过就不能宣称完整实现需求。前两个是技术可行性门槛；第三个既有资料核验，也有真实账户集成验证。当前只批准产品方向并不代表这些门槛已经通过。

## 本轮补上的设计缺口

| 缺口 | v0.2 中的处理 |
| --- | --- |
| 一个审批解决就清除所有 attention | 保存各任务 pending request 集合，多任务统一聚合 |
| 一次工具失败被当作整个任务失败 | 只按任务终态告警；代理正在修复时仍为工作态 |
| 用量轮询错误导致任务 LED 闪烁 | 账单连接与任务观察连接分离；面板分别报告 |
| start/end hook 被视为持续连接 | hook 只负责投递，另行验证持续观察能力；正常 hook 退出不报警 |
| 初始快照和实时流可能漏事件 | 定义缓冲／水位线／连接代次，缺少上游支持时公开限制 |
| 进程崩溃后仍承诺闪灯 | 第一版仅保证宿主存活时的观察断线检测；完整崩溃告警需要单独 watchdog |
| 把充值总额当作百分比分母 | 无套餐上限时只显示余额；个人预算单独标记 |
| 菜单栏隐藏后不能进入设置 | 重新打开应用可进入设置；仅 LED 模式不丢配置入口 |
| 未知状态默认为完成 | 显示未知，保留已有断线告警；不从陈旧缓存伪造当前运行态 |

## 需要用户 review 的四个选择

1. **界面位置**：推荐菜单栏为第一版；侧边浮窗放到后续。
2. **项目范围**：推荐先看 Codex 任务，按项目分组；若要本地服务器／构建状态，需要追加范围。
3. **已终止异常的提示**：推荐快闪保留到用户标记已知晓，或同一任务恢复／明确结束并清理异常；已知晓只清除提示，不改变 Codex 状态。若希望异常一结束立即熄灯，需要修改这条。
4. **故障覆盖**：推荐第一版覆盖观察连接断开；不承诺整个监控应用崩溃后仍能闪灯。若必须覆盖，增加独立 LED 守护组件并单独评审其生命周期。

这四项均为当前建议，不在用户没有答复时视作已批准。
